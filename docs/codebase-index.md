# Codebase Index

A literal, per-file map of this repo — what lives where and what it's for — so a session can jump straight to the right file instead of re-exploring the tree with `find`/`grep` from scratch. This complements the other docs rather than replacing them: `requirements.md`/`backend-service.md`/`frontend-service.md`/`infrastructure.md` cover intent and design (read those for _why_ and _what's planned_); this file covers _what actually exists on disk right now_.

This doc can go stale as files move, get renamed, or get added. If a referenced file or export doesn't exist, trust the live repo over this doc, and treat the mismatch as a signal to refresh this file next time it's touched.

Three packages: `api` (Fastify), `web` (TanStack Start), `shared` (zod schemas, types, constants). Tests: 71 api integration + 12 web unit.

---

## Root

- `.github/workflows/build.yml` — the only workflow (`docs/progress-and-decisions.md` #42). `on: [push, pull_request]`. Job `check`: `postgres:18-alpine` + `axllent/mailpit` service containers, job-level `env` (`DATABASE_URL`, `SMTP_*`, `MAILPIT_URL`), then `corepack enable` → `setup-node` (version from `.nvmrc`, pnpm store cached) → `pnpm install --frozen-lockfile` → `lint`/`typecheck`/`build` → `pnpm --filter …/api migrate` → `test` (the Vitest integration suite runs against the real Postgres + Mailpit, `docs/progress-and-decisions.md` #47). Job `stack`: `docker compose up -d --build --wait --wait-timeout 300`, `curl /healthz`, `db:seed`, `docker compose down -v` — proves the clean-clone path CI-side. No `deploy.yml` / `migrate.yml` — a real deploy pipeline is `docs/production-runbook.md` §6, not built.
- `package.json` / `pnpm-workspace.yaml` / `turbo.json` — pnpm + Turborepo. `typecheck` intentionally `dependsOn: ["^build"]` (not `^typecheck`) — `shared` only emits `dist/index.d.ts` via its `build` script, so dependents need that build to run first or their typecheck can't resolve `@transaction-dispute-portal/shared`'s types.
- `tsconfig.base.json`, `eslint.config.js`, `prettier.config.js` — shared across all three packages; no per-package lint/format config. `eslint.config.js` sets `@typescript-eslint/no-unused-vars: { ignoreRestSiblings: true }` for the `getTableColumns` exclusion idiom (`docs/progress-and-decisions.md` #43), and lists `api/{drizzle,vitest}.config.ts` under `allowDefaultProject` (the api test suite has its own `api/test/tsconfig.json`, auto-discovered by `projectService`).
- `compose.yml`: the only compose file (`docs/progress-and-decisions.md` #42), project name `transaction-dispute-portal`. Five services on compose's default network: `database` (`:5432`), `api` (`:8080`), `web` (`:3000`), `mailpit` (SMTP `:1025`, UI `:8025`), `ntfy` (`:8090`). No reverse proxy (#65). Dev-shaped: whole-repo bind mount + per-package `node_modules` volumes, CHOKIDAR polling, `tsx`/`vite` watch. `api`/`web` run from their package directories (`working_dir: /workspace/api|web`). The api command is `shared build && migrate && dev`; web is `shared build && dev`. `shared/dist` is gitignored, so that build step is what makes a clean `up` work. Postgres credentials are inline under `database.environment`.
- `api/.env` / `web/.env`: committed with **working local values** (#34): `api/.env` has `DATABASE_URL` (host `database`), freshly generated `BETTER_AUTH_SECRET`/`COOKIE_SECRET`, `CORS_ORIGIN`/`FRONTEND_URL=http://localhost:3000`, `NTFY_URL=http://ntfy`, and `SMTP_*` pointed at Mailpit; `web/.env` has `VITE_API_URL=http://localhost:8080`, `VITE_NTFY_URL=http://localhost:8090`, `SERVER_API_URL=http://api:8080`. `.gitignore` ignores `*.env.local` (an optional personal override); `.dockerignore` excludes `.env*` (env is runtime, never baked in).

## api (Fastify backend)

- `src/build.ts` — the `build(logger?)` factory (`docs/progress-and-decisions.md` #35): constructs the Fastify instance (zod type provider, `trustProxy`, 1 MiB body limit, `genReqId` seeding the request id from `x-correlation-id` / `x-request-id`), runs `middlewares(app)` then `route(app)`, awaits `app.ready()`, returns the app **without** calling `listen()`. `logger` is optional so tests build a silent app.
- `src/app.ts` — the process entry point: calls `build(logger)`, wires `close-with-grace` (flip `shutdown.ts`'s flag, `app.close()`, log), then `app.listen({ port: env.PORT, host: "0.0.0.0" })`. Deliberately never imports `src/database/migrate.ts` — `compose.yml` runs `migrate` before `dev`.
- `src/route/index.ts` — mounts every module plugin under its namespace prefix, resolved once from `shared`'s `API_URLS(env.API_VERSION)` (`HEALTH` → `""`, `AUTH` → `/v1/auth`, `CUSTOMER` → `/v1`, `ADMIN` → `/v1/admin`). Registers `check`, `authentication`, `transaction` + `dispute` (under `CUSTOMER`), `admin-dispute` + `admin-invite` (under `ADMIN`).
- `src/type/fastify.ts` — the `declare module "fastify"` augmentation: `FastifyInstance.{authenticate, authorize, connection}` and `FastifyRequest.{startTime, user, session}`.
- `src/middleware/index.ts` — `middlewares(app)`: registers helmet (CSP), `@fastify/cors` (from `env.CORS_ORIGIN`), `@fastify/rate-limit` (global, `env.RATE_LIMIT_*`), `@fastify/cookie` (`env.COOKIE_SECRET`), the zod validator/serializer compilers, `setErrorHandler(error)`, an inline `setNotFoundHandler` sending the shared 404 envelope, the timing/logging hooks, and the `authenticate` / `authorize` / `connection` decorators plus an `onClose` that closes the pool.
- `src/middleware/error.ts` — central error handler → shared envelope: `FST_ERR_VALIDATION` → 422 with `errors[]`, Better Auth `APIError` → 400, `DrizzleQueryError` whose `.cause` is a Postgres `23505` (unique violation) → 409 with per-constraint friendly copy from `CONFLICT_MESSAGE` (`dispute_open_per_transaction_uq_idx` → the one-open-dispute guard #40; `user_email_uq_idx` / `user_email_unique` → the invite-accept dup-account guard #44), any thrown 4xx `statusCode` → that status with the code reverse-looked-up from `HTTP_RESPONSE_CODE`, everything else → 500 (logged). No separate `not-found.ts` — that handler is a 3-line arrow in `middleware/index.ts`.
- `src/middleware/authenticate.ts` — `authenticate` preHandler: reads the Better Auth session (`auth.api.getSession`), 401 + redirect to `FRONTEND_URLS.SIGN_IN` if absent, else attaches `request.user` (`UserModelSelect`) and `request.session` (`SessionModelSelect`).
- `src/middleware/authorize.ts` — `authorize(role | role[])` → a preHandler that 403s unless `request.user.role` is in the allow-list.
- `src/middleware/logging.ts` — `onRequestTimerHook` (stamp `startTime`, echo `x-correlation-id`) and `onResponseLoggingHook` (one structured line per request with method/route/status/`durationMs`/`correlationId`; `/healthz` + `/readyz` excluded).
- `src/lib/logger.ts` — the Pino instance: one `base` options object (level from `env.LOG_LEVEL`, ISO timestamps, `{ level: label }` formatter), with a `pino-pretty` transport spread on only in development. No custom level set (`docs/progress-and-decisions.md` #35).
- `src/lib/shutdown.ts` — a module-level boolean with `setShuttingDown` / `isShuttingDown`; `check`'s probes read it, `app.ts` flips it on signal.
- `src/lib/authentication.ts` — thin wrappers over the Better Auth server API (`sendSignInOtp`, `verifySignInOtp`, `signOut`, `requestEmailChange` → `auth.api.changeEmail`, `confirmEmailChange` → `auth.api.verifyEmail`), converting Fastify headers with `fromNodeHeaders` and returning Better Auth's raw `Response` where the caller needs the cookies. Called only by `modules/authentication/service.ts` (`docs/progress-and-decisions.md` #37/#46).
- `src/lib/security-notifications.ts` — `alertOnNewDeviceLogin(session)`: called from `lib/auth.ts`'s `databaseHooks.session.create.after`. Skips if no `user_agent`; else `repository/session.ts` `hasKnownDeviceSession` (same `user_id` + `user_agent`, different session id) → if unseen, `findUserById` then `sendEmail(buildNewDeviceLoginEmail({ …, signInUrl: env.FRONTEND_URL + FRONTEND_URLS.SIGN_IN }))`. Best-effort, `void`-ed, never awaited into the login response (`docs/backend-service.md` §3, `docs/progress-and-decisions.md` #46). Imports `connection` directly (no request context in a BA hook).
- `src/modules/check/{route,service,type}.ts` — `GET /healthz` (liveness — 503 while draining) and `GET /readyz` (readiness — 503 while draining or if `select 1` doesn't answer within 2s; `docs/progress-and-decisions.md` #35). Responses use `healthzResponseSchema` / `readyzResponseSchema`.
- `src/modules/authentication/{route,service,type}.ts` — `GET /v1/auth/session` (`authenticate` only, no role check — the signed-in user for client route guards, #50), `POST /v1/auth/otp` (send a code; identical response whether or not the account exists; writes `OTP_REQUESTED`; `OTP.MAX_ATTEMPTS`/min per IP), `POST /v1/auth/otp/verify` (exchange code for a session, forward `Set-Cookie`; writes `LOGIN_SUCCESS` / `LOGIN_FAILURE` / `OTP_LOCKED`; `2 × MAX_ATTEMPTS`/min), `POST /v1/auth/change-email` (`{ newEmail }`, `authenticate`; wraps BA `changeEmail` — approval link to the *current* address first; anti-probing 200 copy; writes `EMAIL_CHANGE_REQUESTED`), `POST /v1/auth/change-email/confirm` (`{ token }`, no auth; applies one step; bad/expired token → 401), `POST /v1/auth/sign-out` (unconditional). All go through `lib/authentication.ts` + `repository/auth-audit-log.ts` (`docs/progress-and-decisions.md` #37/#46).
- `src/modules/admin-invite/{route,service,type}.ts` — invite-only admin signup (`docs/progress-and-decisions.md` #44). `GET /v1/admin/invites` (`authenticate` + `authorize(ADMIN)`; a page of the calling admin's invites for the list view — the shared list query #57, `search` on invitee email, `sort` `email|status|created_at|expires_at`; `status` is *derived* — `PENDING`/`ACCEPTED`/`EXPIRED` from `accepted_at`/`expires_at`, `ADMIN_INVITE_STATUS` — so the service translates `?status=` to a SQL predicate and computes each row's `status` field). `POST /v1/admin/invites` (`{ email }`; `409` if an account exists; `randomBytes(32)` hex token, `expires_at = now + ADMIN_INVITE_EXPIRY_HOURS`, real invite email; wire response omits the token). `POST /v1/admin/invites/:token/accept` (no auth — the invitee has no session; `{ name }`, email from the invite; missing token → `404`, used/expired → `409`; one transaction: `acceptAdminInvite` guarded `UPDATE` → `createUser({ role: ADMIN, email_verified: true })`; `redirectUrl: FRONTEND_URLS.SIGN_IN`). Own rate limit (`OTP.MAX_ATTEMPTS * 2`).
- `src/modules/transaction/{route,service,type}.ts` — `GET /v1/transactions` (a page of the caller's own transactions; the shared list query #57 — `search` on merchant name, `from`/`to` on `transacted_at`, `sort` `transacted_at|merchant|amount_cents`) and `GET /v1/transactions/:transactionId` (one transaction, `404` if it isn't the caller's or doesn't exist, `422` if the id is malformed). Both `preHandler: [authenticate, authorize(CUSTOMER)]`. Service converts `Date` columns to ISO strings; the owner filter lives in the `repository/transaction.ts` query, not a post-fetch check (`docs/progress-and-decisions.md` #39). List responses built by `lib/paginated-response.ts`.
- `src/modules/dispute/{route,service,type}.ts` — customer-scoped, `preHandler: [authenticate, authorize(CUSTOMER)]`. `POST /v1/disputes` (open a dispute on one of the caller's own transactions — body `{ transactionId, reason, description }`; ownership miss → `404` per #39; insert + first `dispute_audit_log` row in one `connection.transaction()`; the one-open-dispute rule is the partial unique index + the global 409 handler, no pre-check — `docs/progress-and-decisions.md` #40). `GET /v1/disputes` (a page of the caller's disputes; the shared list query #57 — `search` on description + disputed merchant, `sort` `created_at|merchant|amount_cents|status` — plus optional `status` and `transaction_id` filters, the latter powering the transaction detail page's open-dispute check + history list). `GET /v1/disputes/:disputeId` (one, scoped; other-user/missing → `404`, malformed → `422`). `POST /v1/disputes/:disputeId/withdraw` (close the caller's own open dispute as `WITHDRAWN`; whole handler in one transaction — `findUserDisputeById(..., { lockForUpdate: true })` for a `404`/`409` distinction and an accurate audit `from_status`, then the guarded `withdrawDispute` `UPDATE`; `docs/progress-and-decisions.md` #45). Open/closed checks use `shared`'s `isOpenDisputeStatus`. Wire schema omits `user_id`/`resolved_by`; every response nests the disputed transaction's `merchant_name`/`amount_cents`/`transacted_at` (#53).
- `src/modules/admin-dispute/{route,service,type}.ts` — admin-only, `preHandler: [authenticate, authorize(ADMIN)]` (a customer session → `403`). `GET /v1/admin/disputes` (every customer's disputes for the review queue; the shared list query #57 — `search` also matches the owning customer's name/email, `sort` adds `customer`; with no explicit `sort` the queue orders `status ASC, created_at ASC` so unresolved-and-oldest floats to the top, #58; wire shape = customer's + `user_id` + nested `customer: { name, email }`). `GET /v1/admin/disputes/summary` (one unfiltered `GROUP BY status`, zero-filled to all five — the review-queue stat cards, #58; registered before `:disputeId/review` so `summary` isn't parsed as an id). `POST /v1/admin/disputes/:disputeId/review` (`SUBMITTED → UNDER_REVIEW`; idempotent `200` no-op if already under review; audit row + ntfy publish). `POST /v1/admin/disputes/:disputeId/resolve` (body `{ resolution: RESOLVED|REJECTED, note }`; requires `UNDER_REVIEW` — a still-`SUBMITTED` dispute → `409`; updates `status`/`resolution_note`/`resolved_by`/`resolved_at` + audit row + ntfy, one transaction). Both transitions guard the from-status inside the `UPDATE … WHERE` so concurrent calls collapse to one write (`docs/progress-and-decisions.md` #41). Every response nests the disputed transaction's summary too, merged in from the pre-write `findDisputeById` read (#53).
- `src/database/` — everything database-related lives together here (schema, migrations, connection, migration runner, repository, seed/purge).
- `src/database/executor.ts` — the `Executor` type (`typeof connection | Transaction`): what every `repository/` function takes as its first argument so the caller owns transaction scope (`docs/progress-and-decisions.md` #36).
- `src/database/repository/*.ts` — one file per table of plain hand-written Drizzle functions, re-exported from `index.ts`; modules import from here, never from each other (`docs/progress-and-decisions.md` #36). Pagination totals use `executor.$count(table, where)` where there's no join, else a `select({ value: count() })` mirroring the join. `list-filters.ts` — the shared leaf helpers for the list query (#57): `Page<T>` (`{ rows, total }`), `containsText(term, ...columns)` (case-insensitive `ilike` OR, `LIKE` metacharacters escaped), `withinDays(column, from, to)` (inclusive date-only range; `startOfBusinessDay`/`endOfBusinessDay`, built on `date-fns-tz`'s `fromZonedTime` against the fixed `BUSINESS_TIMEZONE` constant rather than `date-fns`'s ambient-timezone `startOfDay`/`endOfDay`, #60), `withinAmount(column, min, max)` (inclusive cents range on `amount_cents`), `sortDirection(order)` (`asc`/`desc` helper, descending when unset). Each list repo has a `SORT_COLUMN: Record<XSort, PgColumn>` map binding the shared `sort` whitelist to its Drizzle column (can't live in `shared` — some sortable columns are on joined tables). `auth-audit-log.ts` (`recordAuthEvent`; `clamp`s ip/user-agent to 255). `user.ts` (`findUserByEmail` / `findUserById` — full row; `createUser` — `email_verified: true`, sole caller is invite acceptance). `session.ts` (`hasKnownDeviceSession` — same `user_id` + `user_agent`, excluding one session id). `admin-invite.ts` (`createAdminInvite`, `findAdminInviteByToken`, `acceptAdminInvite` — guarded `UPDATE … WHERE token = ? AND accepted_at IS NULL AND expires_at > now()`, #4/#44). `transaction.ts` (`findTransactionsByUser`, `findUserTransactionById` — scoped by `id` **and** `user_id`, #39). `dispute.ts` (`findDisputesByUser` / `findUserDisputeById` — customer, scoped, columns via `getTableColumns` rest-spread excluding `user_id`/`resolved_by`, #43; both `innerJoin` `TransactionModel` and select a nested `transaction: TRANSACTION_SUMMARY_COLUMNS`, #53; `findDisputesByUser` takes an optional `transactionId` filter; `findUserDisputeById` takes an optional `{ lockForUpdate }` for `SELECT … FOR UPDATE`, #45; `findDisputesForReview` / `findDisputeById` — admin, full row, same transaction join **plus an `innerJoin` on `UserModel`** for a nested `customer: { name, email }` (#58); `findDisputesForReview`'s default `orderBy` is `status ASC, created_at ASC, id DESC` unless an explicit `sort` overrides (#58); `countDisputesByStatus` — one `GROUP BY status`, zero-filled to all five, for the summary endpoint (#58); `markDisputeUnderReview` / `resolveDispute` / `withdrawDispute` — the from-status is in the `UPDATE … WHERE`, empty `RETURNING` is the caller's 409, #41/#45, no join (an `UPDATE … RETURNING` can't join — the service layer merges in the transaction from a prior read instead, #53); `createDispute`, same). `dispute-audit-log.ts` (`recordDisputeStatusChange` — one row per transition: actor, from/to status, note).
- `src/database/seed.ts` — `pnpm --filter …/api db:seed`: deterministic (`faker.seed`) seed — truncates the data tables, then inserts ~31 users (the `admin@gmail.com` admin, a long-history `customer@gmail.com`, a no-disputes `newcomer@gmail.com`, ~28 faker customers), one `KNOWN_DEVICE_USER_AGENT` session each for the admin + demo customer (so the new-device alert is quiet on a known device, `docs/backend-service.md` §3), ~4.6k ZAR-cent transactions with SA merchant names spread over 14 months (`date-fns` `subMonths`), ~260 disputes across every status/reason (including `WITHDRAWN`, ~7%) on distinct transactions, and one `dispute_audit_log` row per status transition (a `SUBMITTED → WITHDRAWN` row for withdrawn ones). Own single (`max: 1`) connection, reads `process.env.DATABASE_URL` directly like `migrate.ts`.
- `src/database/purge.ts` — `pnpm --filter …/api db:purge`: `TRUNCATE ... RESTART IDENTITY CASCADE` every `public` table except drizzle's migration ledger. Leaves the schema intact.
- `src/database/schema/*.ts` — one table per file, Ubuntu Stories house style (`docs/progress-and-decisions.md` #28): `user`, `session`, `account`, `verification` (Better Auth tables, our columns + `fields` maps in `lib/auth.ts`); `transaction`, `dispute`, `dispute-audit-log`, `admin-invite`, `auth-audit-log` (domain). Each exports `XxxModel` + `XxxModelInsert`/`Select`/`UniqueWhere` types; `pgEnum`s (`userRole`, `disputeStatus` incl. `WITHDRAWN`, `disputeReason`, `authEvent` incl. `EMAIL_CHANGE_REQUESTED`) built from `shared/src/constant.ts` SCREAMING_SNAKE constants (#30). Every PK is `uuid` defaulting to Postgres 18 native `sql\`uuidv7()\`` (#29). `user.name` is `NOT NULL`. `dispute.ts` carries the partial unique index for the one-open-dispute guard (#4/#28/#40) and a `resolved_by` FK to `user`. `admin-invite.ts` has a unique `token`, an `invited_by` FK to `user`, and `email` / `invited_by` / `updated_at` indexes (#44). `relations.ts` holds every `relations()` call centrally.
- `src/database/schema/index.ts` — barrel: re-exports all nine table files then `relations.js`. `drizzle-kit generate` reads this.
- `src/database/migrations/`: generated SQL, committed. One migration, `000_init.sql`, creates all nine tables, enums and indexes; `meta/` holds the drizzle-kit snapshot/journal. The schema is pre-deployment, so it's regenerated in place rather than stacked (`docker compose down -v` to re-create the dev DB). `compose.yml` runs it on api start (#42).
- `src/database/config.ts` — the app's pooled `postgres-js` connection + `drizzle()` instance (`connection`), for query code once routes exist. `globalThis`-cached singleton (same pattern as Ubuntu Stories) — `tsx watch` hot-reloads this module on every save, and a naive `postgres()` call here would leak a connection per reload. Throws at import time if `DATABASE_URL` is unset.
- `src/database/migrate.ts` — standalone migration runner, its own single (`max: 1`) short-lived connection (deliberately not `config.ts`'s pool, `onnotice` silenced), applies SQL from `src/database/migrations` via `drizzle-orm`'s runtime migrator and exits. Never imported by `app.ts`. Run via `pnpm --filter @transaction-dispute-portal/api migrate` — `compose.yml` chains it before the dev server on api start (`docs/progress-and-decisions.md` #42); production runs it as a gated pre-deploy step (`docs/production-runbook.md` §3). A runtime script rather than `drizzle-kit migrate`, so it works without devDependencies.
- `src/lib/env.ts` — zod-validated `process.env` singleton (`docs/progress-and-decisions.md` #28): parsed once, cached, `process.exit(1)` with a per-key report on failure. Includes `NTFY_URL` (default `http://ntfy`). Every module imports the typed `env`, never `process.env`.
- `src/lib/auth.ts` — the Better Auth instance (`docs/progress-and-decisions.md` #21/#28/#46): `drizzleAdapter` over `config.ts`'s `connection` with the four Better Auth tables mapped field-by-field to our snake_case columns; `emailAndPassword` off; `emailOTP` plugin only (length / hashed / `disableSignUp` / expiry / attempts all from `shared`'s `OTP` constant) with `sendVerificationOTP` calling `mailer.ts`; `emailVerification.sendVerificationEmail` + `user.changeEmail.{enabled, sendChangeEmailConfirmation}` wire the two-step email-change flow (`email-verification.ts` / `email-change-approval.ts` builders, `EMAIL_CHANGE_TOKEN_EXPIRY_MINUTES`); `databaseHooks.session.create.after` → `alertOnNewDeviceLogin` (`void`-ed); `basePath` from `API_URLS(env.API_VERSION).AUTH`; `additionalFields.role` typed as `Object.values(USER_ROLE)` with `input: false` + `defaultValue: CUSTOMER`, so Better Auth infers `user.role` as `"ADMIN" | "CUSTOMER"` and `authenticate.ts` needs no cast/parse/fallback; `advanced.database.generateId` → `util.ts` v7; Better Auth's own `rateLimit` disabled (#35).
- `src/lib/mailer.ts` — `nodemailer` transport from `env` + `sendEmail({ to, subject, html })` that logs-and-swallows failures (Better Auth "don't await OTP" timing advice). One file, not Ubuntu Stories' transport/mailer split (`docs/progress-and-decisions.md` #31).
- `src/lib/notifier.ts` — `publishDisputeUpdate(userId, { dispute_id, status })`: a fire-and-forget `fetch` POST to `${env.NTFY_URL}/dispute-updates-${userId}` with that JSON as the body (#66), `AbortSignal.timeout(2000)`, failures logged not thrown (same posture as `mailer.ts`). Called by `modules/admin-dispute` on `review` / `resolve` (`docs/dev-tools.md`, `docs/progress-and-decisions.md` #41).
- `src/lib/util.ts` — `generateUuid()` (`uuid` package v7, for Better Auth's app-side ID generation) and `withTimeout(promise, ms)` (used by `readyz`'s DB probe).
- `src/lib/paginated-response.ts` — `paginatedResponse({ query, total, rows, message })`: the list-response envelope (`count` = full match total, `total` = rows on this page, `page`/`limit` from the query) as a plain object, so the zod serializer still typechecks it against each route's response schema.
- `src/email/*.ts` — plain builders returning `EmailContent` (`{ to, subject, html }`), no registry (`docs/progress-and-decisions.md` #31). `otp-email-sign-in-request.ts` (sign-in code), `admin-invite.ts` (invite link, #44), `new-device-login.ts` (takes an absolute `signInUrl`), `email-change-approval.ts` (approval link to the *old* address), `email-verification.ts` (verification link to the *new* address).
- `drizzle.config.ts` — `drizzle-kit` config (`dialect: postgresql`, `schema`/`out` under `src/database/`, `strict`/`verbose` on, `DATABASE_URL` from env). Only used locally/in CI to run `generate`/`check`; `drizzle-kit` itself never ships in the production image.
