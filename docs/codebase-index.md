# Codebase Index

A literal, per-file map of this repo — what lives where and what it's for — so a
session can jump straight to the right file instead of re-exploring the tree
with `find`/`grep` from scratch. This complements the other docs rather than
replacing them: `brief.md`/`api.md`/`domain-model.md`/`scaling-and-resilience.md`
cover intent and design (read those for _why_ and _what's planned_), this file
covers _what actually exists on disk right now_.

This doc can go stale as files move, get renamed, or get added. If a
referenced file or export doesn't exist, trust the live repo over this doc,
and treat the mismatch as a signal to refresh this file next time it's touched.

**Status: schema + auth wired, no request handlers yet.** The full Drizzle schema (`docs/domain-model.md` entities + Better Auth tables), the Better Auth config, env validation, and OTP email delivery all exist and are verified (migration applies clean on `postgres:18`, an OTP email lands in Mailpit end to end). `api/src/app.ts` is still a bare `/healthz` skeleton — no routes, loaders, or UI yet. `web` is unchanged placeholder. `pnpm install`, `build`, `typecheck`, `lint`, `format`, both dev servers, and both production Docker images have all been run successfully. Don't let this file drift behind the real tree — refresh it whenever a session touches a part of the repo it doesn't yet describe accurately.

## Root

- `.github/workflows/build.yml` — standalone on PRs and any non-`main` push (`pull_request:`/`push: branches-ignore: [main]`), and also invokable via `workflow_call:` — `deploy.yml` calls it as the first job of its own run (`docs/decisions.md` #26), so it no longer runs a second, separate time on `main` pushes. Job 1: `corepack enable` → `setup-node` (version from `.nvmrc`, pnpm store cached) → `pnpm install --frozen-lockfile` → `lint`/`typecheck`/`build`/`test`. Job 2: builds both production Dockerfiles (`api`, `web`) as a matrix, catching the class of bug found while scaffolding this repo (missing `rootDir`, the `srvx` wrapper, `node_modules` in the runtime stage) before merge instead of at submission time. `pnpm test` currently succeeds trivially — no package defines a `test` script yet; this starts failing loudly the moment Vitest tests are added without wiring, which is the intent.
- `.github/workflows/deploy.yml` — the CD half, split from `build.yml` so "build" and "deploy" are separately visible in the Actions tab (`docs/decisions.md` #24). Triggers only on `push` to `main`. Two jobs, one connected graph: `build` (calls `build.yml` via `uses:`, not `workflow_run` — `docs/decisions.md` #26) → `staging` (`needs: build`, `environment: staging`, matrix over `api`/`web`, builds each production `Dockerfile` and pushes to GHCR tagged `latest`/`staging`/`sha-<commit>`). No production tier — no live infra and none planned, so staging is the only target and takes `latest` (`docs/decisions.md` #34). Image tags built explicitly from `github.sha`, not `docker/metadata-action` (`docs/decisions.md` #25).
- `.github/workflows/migrate.yml` — manually-triggered (`workflow_dispatch`, no inputs) DB migration against the `staging` environment (`docs/decisions.md` #33/#34). Runs `drizzle-kit check` (drift catch, no DB needed), then a guard that fails with setup instructions if the `staging` `DATABASE_URL` secret is unset, then `pnpm --filter @transaction-dispute-portal/api migrate`. Dormant until that secret exists.
- `package.json` / `pnpm-workspace.yaml` / `turbo.json` — pnpm + Turborepo. `typecheck` intentionally `dependsOn: ["^build"]` (not `^typecheck`) — `shared` only emits `dist/index.d.ts` via its `build` script, so dependents need that build to run first or their typecheck can't resolve `@transaction-dispute-portal/shared`'s types.
- `tsconfig.base.json`, `eslint.config.js`, `prettier.config.js` — shared across all three packages; no per-package lint/format config. `eslint.config.js` ignores `web/server.mjs` (plain runtime `.mjs`, not part of any tsconfig program, so typescript-eslint's project service can't type-check it).
- `compose.yml` — the **staging base** and the merge base (`docs/decisions.md` #32/#34). Postgres (labeled local stand-in) + api + web, built from the production `Dockerfile`s, no bind mounts, no Mailpit, DB not published. Reads `./api/.env` / `./web/.env` / `./env/.env.database` directly. Staging dry-run: `docker compose -f compose.yml up --build`. Distinct `image:` names from the override so a bare `docker compose up` never reuses a staging image for the dev stack.
- `compose.override.yml` — the **development deltas** (`docs/decisions.md` #32), auto-merged by any bare `docker compose` command so `docker compose up` alone gives the dev stack. Per service, overrides only what differs: dev `Dockerfile`s, whole-repo bind mount + `*-node_modules` volumes, CHOKIDAR polling, 90s healthcheck `start_period`, published `5432`. Adds the `transaction-dispute-portal-mailpit` service (SMTP catcher, `localhost:8025`, `mailpit` network alias for `SMTP_HOST`). Inherits the base's `env_file` — no `env_file` block of its own.
- `api/.env` / `web/.env` / `env/.env.database` — committed env files with **working local values** (`docs/decisions.md` #34): `api/.env` has a real `DATABASE_URL` + `BETTER_AUTH_SECRET`/`COOKIE_SECRET` (freshly generated, local-only); `env/.env.database` a real `POSTGRES_PASSWORD`; `web/.env` no secrets. `SMTP_*` points at Mailpit. No comments. Used by both compose files. `.gitignore` ignores only `*.env.local` (an optional personal override); `.dockerignore` keeps `.env*` globs (env is runtime, never baked).

## api (Fastify backend)

- `src/app.ts` — placeholder entry point: a bare Fastify instance with `/healthz` and `/readyz` routes, listening on `PORT` (default 8080). Verified booting via both `pnpm dev` and the built Docker image. Replace with a real `build()`/`app.ts` split (a `build()` factory that wires plugins/routes, separate from the `app.ts` that calls `listen()`) once routes land — auth/drizzle/env now exist under `src/lib` and `src/database` but nothing mounts them yet. Deliberately never imports `src/database/migrate.ts` — migrations are a separate step, not run on API boot (`docs/decisions.md` #24).
- `src/database/` — everything database-related lives together here (schema, migrations, connection, migration runner), unlike Ubuntu Stories' split between `src/drizzle/` and `src/lib/database.ts` — see `docs/decisions.md` #24 for why.
- `src/database/schema/*.ts` — one table per file, Ubuntu Stories house style (`docs/decisions.md` #28): `user`, `session`, `account`, `verification` (Better Auth tables, our columns + `fields` maps in `lib/auth.ts`); `transaction`, `dispute`, `dispute-audit-log`, `admin-invite`, `auth-audit-log` (domain). Each exports `XxxModel` + `XxxModelInsert`/`Select`/`UniqueWhere` types; `pgEnum`s (`userRole`, `disputeStatus`, `disputeReason`, `authEvent`) built from `shared/src/constant.ts` SCREAMING_SNAKE constants (#30). Every PK is `uuid` defaulting to Postgres 18 native `sql\`uuidv7()\`` (#29). `dispute.ts` carries the partial unique index for the one-open-dispute guard (#4/#28). `relations.ts` holds every `relations()` call centrally.
- `src/database/schema/index.ts` — barrel: re-exports all nine table files then `relations.js`. `drizzle-kit generate` reads this.
- `src/database/migrations/` — generated SQL, committed. `0000_daily_forge.sql` creates all nine tables + enums + indexes; `meta/` snapshots. Copied into the production image alongside `dist/` (`Dockerfile`) so `dist/database/migrate.js` has something to apply. Applies clean on `postgres:18` (verified, plus an idempotent re-run).
- `src/database/config.ts` — the app's pooled `postgres-js` connection + `drizzle()` instance (`connection`), for query code once routes exist. `globalThis`-cached singleton (same pattern as Ubuntu Stories) — `tsx watch` hot-reloads this module on every save, and a naive `postgres()` call here would leak a connection per reload. Throws at import time if `DATABASE_URL` is unset.
- `src/database/migrate.ts` — standalone migration runner, its own single (`max: 1`) short-lived connection (deliberately not `config.ts`'s pool, `onnotice` silenced), applies SQL from `src/database/migrations` via `drizzle-orm`'s runtime migrator and exits. Never imported by `app.ts`. Run via `pnpm --filter @transaction-dispute-portal/api migrate` (dev, `tsx`), `node dist/database/migrate.js` (prod), or `.github/workflows/migrate.yml` (`docs/decisions.md` #33). Custom runtime script rather than Ubuntu Stories' `npx drizzle-kit migrate` because it must work with no devDependencies present (`docs/decisions.md` #24).
- `src/lib/env.ts` — zod-validated `process.env` singleton (`docs/decisions.md` #28): parsed once, cached, `process.exit(1)` with a per-key report on failure. Every module imports the typed `env`, never `process.env`.
- `src/lib/auth.ts` — the Better Auth instance (`docs/decisions.md` #21/#28): `drizzleAdapter` over `config.ts`'s `connection` with the four Better Auth tables mapped field-by-field to our snake_case columns; `emailAndPassword` off; `emailOTP` plugin only (6-digit, hashed, `disableSignUp`, 10-min expiry, 5 attempts) with `sendVerificationOTP` calling `mailer.ts`; `advanced.database.generateId` → `util.ts` v7; per-account rate limiting from `env`.
- `src/lib/mailer.ts` — `nodemailer` transport from `env` + `sendEmail({ to, subject, html })` that logs-and-swallows failures (Better Auth "don't await OTP" timing advice). One file, not Ubuntu Stories' transport/mailer split (`docs/decisions.md` #31).
- `src/lib/util.ts` — `generateUuid()` (`uuid` package v7), for Better Auth's app-side ID generation.
- `src/email/otp-email-sign-in-request.ts` — builder returning `{ to, subject, html }` for the sign-in OTP email. The only template so far; more (recovery/invite, `docs/auth.md` §3) land here as plain builders, no registry (`docs/decisions.md` #31).
- `drizzle.config.ts` — `drizzle-kit` config (`dialect: postgresql`, `schema`/`out` under `src/database/`, `strict`/`verbose` on, `DATABASE_URL` from env). Only used locally/in CI to run `generate`/`check`; `drizzle-kit` itself never ships in the production image.
- `package.json` — scripts: `dev` (tsx watch), `build` (tsc), `start` (node dist), `typecheck`, `lint`, `generate`, `migrate`, `clean`. Dependencies: `better-auth`, `drizzle-orm`, `fastify`, `nodemailer`, `postgres`, `uuid`, `zod`; devDependency: `drizzle-kit`. Exact pins only (`.npmrc` `save-exact=true`).
- `tsconfig.json` — extends root `tsconfig.base.json`; `rootDir`/`outDir` set explicitly (tsc errors without `rootDir` once `outDir` is set on a single-directory `include`).
- `Dockerfile` — production multi-stage (deps → build → prod-deps → runtime), non-root `node` user, no devDependencies or source in the final image. Also copies `src/database/migrations` (static SQL, not compiled) into the runtime image so `dist/database/migrate.js` has migrations to apply. Verified: builds, and the running container answers `/healthz` on port 8080; separately verified `node dist/database/migrate.js` runs inside the built image and fails cleanly without `DATABASE_URL`.
- `Dockerfile.dev` — installs the whole workspace, runs `pnpm --filter @transaction-dispute-portal/api dev` with source bind-mounted via `compose.yml`.

## web (TanStack Start frontend)

- `src/routes/__root.tsx` / `src/routes/index.tsx` — placeholder route tree: a single index route rendering "Transactions Dispute Portal". Replace with real routes/loaders once the UI work starts. No UI kit/shadcn, forms, query client, or auth client yet — deliberately bare.
- `src/router.tsx` — TanStack Router instance wiring the generated route tree (`src/routeTree.gen.ts`, auto-generated by the router's Vite plugin on `dev`/`build` — don't hand-edit it).
- `server.mjs` — the production entry point. TanStack Start's `vite build` emits `dist/server/server.js` as a **bare Web-standard `fetch` handler with no attached runtime** (confirmed by inspecting the build output and the `@tanstack/react-start` package — it's meant to be wrapped by a hosting adapter, not run directly). `server.mjs` wraps it with `srvx` (already a transitive dependency, promoted to direct) to get an actual Node HTTP server: `serve({ fetch: handler.fetch, port, hostname: "0.0.0.0" })`. Running `node dist/server/server.js` directly does nothing and exits 0 silently — this tripped up the first pass at the production Dockerfile.
- `package.json` — scripts: `dev` (vite dev), `build` (vite build), `start` (`node server.mjs`), `typecheck`, `lint`, `clean`.
- `tsconfig.json` — extends root `tsconfig.base.json`; includes `server.mjs` for typecheck (excluded from eslint, see Root section).
- `Dockerfile` — production multi-stage. The SSR build externalizes `react`/`react-dom` rather than bundling them (confirmed the hard way: the first build crashed at runtime with `ERR_MODULE_NOT_FOUND: react`), so unlike a typical "static output" frontend image, the runtime stage still needs `node_modules` (root + `web`) alongside `dist/` and `server.mjs`. Verified: builds, and the running container serves the SSR page on port 3000.
- `Dockerfile.dev` — installs the whole workspace, runs `pnpm --filter @transaction-dispute-portal/web dev --host 0.0.0.0` with source bind-mounted via `compose.yml`.

## shared (types shared between api and web)

- `src/index.ts` — barrel export: `constant.ts` + `schema/field.ts` + `schema/global.ts` so far. `Transaction`/`Dispute`/`DisputeReason`/etc. (see `docs/domain-model.md`) still land here once the schema is decided.
- `src/constant.ts` — `APP_NAME`; `HTTP_CODE`/`HTTP_RESPONSE_CODE`, `ORDER_DIRECTION`, `DEFAULT_PAGE_LIMIT`/`NUMBER` (response-envelope support, `docs/decisions.md` #22); and the domain/auth enum constants `USER_ROLE`, `DISPUTE_STATUS`, `DISPUTE_REASON`, `OPEN_DISPUTE_STATUS`, `AUTH_EVENT` — all SCREAMING_SNAKE values (`docs/decisions.md` #30), consumed by the `pgEnum`s in `api/src/database/schema` and the API wire contract.
- `src/schema/field.ts` — `stringSchema`, `numberSchema`, `httpCodeSchema`, `orderDirectionSchema`: the minimal primitive-schema subset `schema/global.ts` needs. More get added here as concrete callers need them, not speculatively.
- `src/schema/global.ts` — `globalResponseSchema`/`paginatedGlobalResponseSchema`/`paginationSortAndSearchQuerySchema`. This is the default response envelope for every API response — see `docs/api.md` "Response envelope" and `docs/decisions.md` #22.
- `package.json` — `exports` points at `dist/index.js`/`dist/index.d.ts` (compiled), not `src/index.ts` directly — `api`'s production image ships a compiled `dist/app.js` run by plain `node`, which can't resolve a `.ts` import target. `dev` script (`tsc --watch`) keeps `dist/` fresh locally — `turbo dev` runs it in parallel with `api`/`web`'s own dev servers. All relative imports within `shared/src` use explicit `.js` extensions for this same reason — `moduleResolution: "Bundler"` doesn't rewrite them, and plain Node ESM requires them (caught while building `docs/decisions.md` #22's schema files: `tsc` passed, plain `node` on the compiled output didn't, until fixed).
- `package.json` dependencies — `zod@4.4.3` (already resolved in the lockfile as a transitive dependency before this).
- `tsconfig.json` — extends root `tsconfig.base.json`; `rootDir`/`outDir` set explicitly (same `rootDir` requirement as `api`).
