# Codebase Index

A literal, per-file map of this repo — what lives where and what it's for — so a
session can jump straight to the right file instead of re-exploring the tree
with `find`/`grep` from scratch. This complements the other docs rather than
replacing them: `brief.md`/`api.md`/`domain-model.md`/`scaling-and-resilience.md`
cover intent and design (read those for _why_ and _what's planned_), this file
covers _what actually exists on disk right now_.

This doc can go stale as files move, get renamed, or get added. If a
referenced file or export doesn't exist, trust the live repo over this doc,
and treat the mismatch as a signal to refresh this file next time it's touched.

**Status: initial scaffold — no domain business logic yet.** `api`/`web` are still empty-but-verified-runnable skeletons; `shared` has real, generic infrastructure (response envelope schemas, `docs/decisions.md` #22) but no domain types yet. `pnpm install`, `build`, `typecheck`, `lint`, `format`, both dev servers, and both production Docker images have all been run successfully against this exact scaffold. Fill this in for real once the domain model/API/UI land. Don't let it drift far behind the real tree — refresh it whenever a session touches a part of the repo this file doesn't yet describe accurately.

## Root

- `.github/workflows/build.yml` — runs on every push/PR to `main`. Job 1: `corepack enable` → `setup-node` (version from `.nvmrc`, pnpm store cached) → `pnpm install --frozen-lockfile` → `lint`/`typecheck`/`build`/`test`. Job 2: builds both production Dockerfiles (`api`, `web`) as a matrix, catching the class of bug found while scaffolding this repo (missing `rootDir`, the `srvx` wrapper, `node_modules` in the runtime stage) before merge instead of at submission time. `pnpm test` currently succeeds trivially — no package defines a `test` script yet; this starts failing loudly the moment Vitest tests are added without wiring, which is the intent.
- `.github/workflows/deploy.yml` — the CD half, split from `build.yml` so "build" and "deploy" are separately visible in the Actions tab (`docs/decisions.md` #24). Two jobs: `staging` (`environment: staging`, no gate — runs automatically whenever `build.yml` succeeds on `main`, tags `staging`/`sha-<commit>`) and `production` (`environment: production`, triggers automatically on a `v*` tag push but pauses for a required-reviewer approval configured on that environment in repo Settings, tags `latest`/the tag name — `docs/decisions.md` #25). Tags are built explicitly from event context, not via `docker/metadata-action`'s auto-detection, which failed on the first real run (`docs/decisions.md` #25). No live infra to deploy to (out of scope, see `CLAUDE.md`), so this is the honest boundary: publish a versioned, deployable artifact, stop there.
- `package.json` / `pnpm-workspace.yaml` / `turbo.json` — pnpm + Turborepo. `typecheck` intentionally `dependsOn: ["^build"]` (not `^typecheck`) — `shared` only emits `dist/index.d.ts` via its `build` script, so dependents need that build to run first or their typecheck can't resolve `@transaction-dispute-portal/shared`'s types.
- `tsconfig.base.json`, `eslint.config.js`, `prettier.config.js` — shared across all three packages; no per-package lint/format config. `eslint.config.js` ignores `web/server.mjs` (plain runtime `.mjs`, not part of any tsconfig program, so typescript-eslint's project service can't type-check it).
- `compose.yml` — Postgres + api + web dev stack, `transaction-dispute-portal-*` container naming. Builds api/web from their `Dockerfile.dev`.
- `env/development/.env.database` / `api/.env` / `web/.env` — the committed local dev env files. Every secret-shaped key in `api/.env` (`DATABASE_URL`, `BETTER_AUTH_SECRET`, `COOKIE_SECRET`) and `env/development/.env.database` (`POSTGRES_PASSWORD`) is blank — see `docs/decisions.md` #20; non-secret config stays real. `web/.env` has no secrets, nothing blanked. `.gitignore` allowlists exactly these three paths; any `.env.local`/`.env.local.database` file (real values, no committed template — README.md "Local setup" has the steps) stays ignored.
- `compose.yml` loads `api/.env.local` and `env/development/.env.local.database` as optional (`required: false`) second `env_file` entries, overriding the committed files' blank values when present — nothing errors if they're absent, they're just not there yet on a fresh clone.
- `mailpit` service in `compose.yml` — local SMTP catcher for every login's OTP code (`docs/decisions.md` #21) plus account-recovery/invite email (`docs/auth.md` §3); view caught mail at `localhost:8025`. No real email account needed for local dev — logging in yourself means reading your own OTP code there.

## api (Fastify backend)

- `src/app.ts` — placeholder entry point: a bare Fastify instance with `/healthz` and `/readyz` routes, listening on `PORT` (default 8080). Verified booting via both `pnpm dev` and the built Docker image. Replace with a real `build()`/`app.ts` split (a `build()` factory that wires plugins/routes, separate from the `app.ts` that calls `listen()`) once auth/routes/drizzle land. Deliberately never imports `src/database/migrate.ts` — migrations are a separate step, not run on API boot (`docs/decisions.md` #24).
- `src/database/` — everything database-related lives together here (schema, migrations, connection, migration runner), unlike Ubuntu Stories' split between `src/drizzle/` and `src/lib/database.ts` — see `docs/decisions.md` #24 for why.
- `src/database/schema/index.ts` — Drizzle schema barrel, empty so far (`export {}`). Per-entity files (`docs/domain-model.md`) land here and get re-exported, mirroring Ubuntu Stories' `src/drizzle/schema` layout (renamed `drizzle` → `database` here); `drizzle-kit generate` reads this barrel.
- `src/database/migrations/` — generated SQL migrations (`generate` script output), committed; currently just the empty `meta/_journal.json` `drizzle-kit generate` scaffolds since no tables exist yet. Copied into the production image alongside `dist/` (`Dockerfile`) so `dist/database/migrate.js` has something to apply.
- `src/database/config.ts` — the app's pooled `postgres-js` connection + `drizzle()` instance, for query code once routes exist. `globalThis`-cached singleton (same pattern as Ubuntu Stories) — `tsx watch` hot-reloads this module on every save, and a naive `postgres()` call here would leak a connection per reload. Throws at import time if `DATABASE_URL` is unset.
- `src/database/migrate.ts` — standalone migration runner, its own single (`max: 1`) short-lived connection (deliberately not `config.ts`'s pool), applies SQL from `src/database/migrations` via `drizzle-orm`'s runtime migrator and exits. Never imported by `app.ts`. Run via `pnpm --filter @transaction-dispute-portal/api migrate` (dev, `tsx`) or `node dist/database/migrate.js` (prod — compiles alongside `dist/app.js`, works with no devDependencies present; this is why it's a custom runtime script rather than Ubuntu Stories' `npx drizzle-kit migrate`, see `docs/decisions.md` #24).
- `drizzle.config.ts` — `drizzle-kit` config (`dialect: postgresql`, `schema`/`out` under `src/database/`, `strict`/`verbose` on, `DATABASE_URL` from env). Only used locally/in CI to run `generate`; `drizzle-kit` itself never ships in the production image.
- `package.json` — scripts: `dev` (tsx watch), `build` (tsc), `start` (node dist), `typecheck`, `lint`, `generate`, `migrate`, `clean`. Dependencies: `drizzle-orm`, `postgres` (postgres.js driver); devDependency: `drizzle-kit`.
- `tsconfig.json` — extends root `tsconfig.base.json`; `rootDir`/`outDir` set explicitly (tsc errors without `rootDir` once `outDir` is set on a single-directory `include`).
- `Dockerfile` — production multi-stage (deps → build → prod-deps → runtime), non-root `node` user, no devDependencies or source in the final image. Also copies `src/database/migrations` (static SQL, not compiled) into the runtime image so `dist/database/migrate.js` has migrations to apply. Verified: builds, and the running container answers `/healthz` on port 8080; separately verified `node dist/database/migrate.js` runs inside the built image and fails cleanly without `DATABASE_URL`.
- `Dockerfile.dev` — installs the whole workspace, runs `pnpm --filter @transaction-dispute-portal/api dev` with source bind-mounted via `compose.yml`.

## web (TanStack Start frontend)

- `src/routes/__root.tsx` / `src/routes/index.tsx` — placeholder route tree: a single index route rendering "Transactions Dispute Portal". Replace with real routes/loaders once the UI work starts. No UI kit/shadcn, forms, query client, or auth client yet — deliberately bare.
- `src/router.tsx` — TanStack Router instance wiring the generated route tree (`src/routeTree.gen.ts`, auto-generated by the router's Vite plugin on `dev`/`build` — don't hand-edit it).
- `server.mjs` — the production entry point. TanStack Start's `vite build` emits `dist/server/server.js` as a **bare Web-standard `fetch` handler with no attached runtime** (confirmed by inspecting the build output and the `@tanstack/react-start` package — it's meant to be wrapped by a hosting adapter, not run directly). `server.mjs` wraps it with `srvx` (already a transitive dependency, promoted to direct) to get an actual Node HTTP server: `serve({ fetch: handler.fetch, port, hostname: "0.0.0.0" })`. Running `node dist/server/server.js` directly does nothing and exits 0 silently — this tripped up the first pass at the production Dockerfile.
- `package.json` — scripts: `dev` (vite dev), `build` (vite build), `start` (`node server.mjs`), `typecheck`, `lint`, `clean`.
- `tsconfig.json` — extends root `tsconfig.base.json`; includes `server.mjs` for typecheck (excluded from eslint, see Root section).
- `Dockerfile` — production multi-stage. The SSR build externalizes `react`/`react-dom` rather than bundling them (confirmed the hard way: the first build crashed at runtime with `ERR_MODULE_NOT_FOUND: react`), so unlike a typical "static output" frontend image, the runtime stage still needs `node_modules` (root + `web`) alongside `dist/` and `server.mjs`. Verified: builds, and the running container serves the SSR page on port 3000.
- `Dockerfile.dev` — installs the whole workspace, runs `pnpm --filter @transaction-dispute-portal/web dev --host 0.0.0.0` with source bind-mounted via `compose.yml`.

## shared (types shared between api and web)

- `src/index.ts` — barrel export: `constant.ts` + `schema/field.ts` + `schema/global.ts` so far. `Transaction`/`Dispute`/`DisputeReason`/etc. (see `docs/domain-model.md`) still land here once the schema is decided.
- `src/constant.ts` — `HTTP_CODE`/`HTTP_RESPONSE_CODE`, `ORDER_DIRECTION`, `DEFAULT_PAGE_LIMIT`/`NUMBER`. Kept intentionally minimal — only what the response-envelope schemas below actually need (`docs/decisions.md` #22).
- `src/schema/field.ts` — `stringSchema`, `numberSchema`, `httpCodeSchema`, `orderDirectionSchema`: the minimal primitive-schema subset `schema/global.ts` needs. More get added here as concrete callers need them, not speculatively.
- `src/schema/global.ts` — `globalResponseSchema`/`paginatedGlobalResponseSchema`/`paginationSortAndSearchQuerySchema`. This is the default response envelope for every API response — see `docs/api.md` "Response envelope" and `docs/decisions.md` #22.
- `package.json` — `exports` points at `dist/index.js`/`dist/index.d.ts` (compiled), not `src/index.ts` directly — `api`'s production image ships a compiled `dist/app.js` run by plain `node`, which can't resolve a `.ts` import target. `dev` script (`tsc --watch`) keeps `dist/` fresh locally — `turbo dev` runs it in parallel with `api`/`web`'s own dev servers. All relative imports within `shared/src` use explicit `.js` extensions for this same reason — `moduleResolution: "Bundler"` doesn't rewrite them, and plain Node ESM requires them (caught while building `docs/decisions.md` #22's schema files: `tsc` passed, plain `node` on the compiled output didn't, until fixed).
- `package.json` dependencies — `zod@4.4.3` (already resolved in the lockfile as a transitive dependency before this).
- `tsconfig.json` — extends root `tsconfig.base.json`; `rootDir`/`outDir` set explicitly (same `rootDir` requirement as `api`).
